# 측정 결과

보고서에 넣을 TCP / UDP / UDP+NACK 비교 데이터. 측정일 2026-11-24.

## 측정 방법

- PC 한 대에서 서버랑 PC 테스트 클라이언트를 같이 띄움 (127.0.0.1, 실제 소켓 사용)
- 영상: 테스트 패턴 1280x720 30fps, 화질 720p 고정 (영상 2500k + 음성 128k, TS로 약 2.8Mbps), 인코더 h264_nvenc
- 네트워크 조건은 서버의 열화 시뮬레이터로 만듦
- 조건마다 처음부터 30초 재생, 1초 단위로 기록. 평균은 처음 3초(시작 구간)를 빼고 계산
- 스크립트: `pc/tools/measure.py` (측정), `pc/tools/summarize.py` (요약)

파일

- `raw.csv` : 1초 단위 원본 (조건 6 x 방식 3 x 30초)
- `runs.csv` : 실행별 서버 쪽 카운터 (보낸 패킷, 재전송, 버린 패킷)
- `summary.csv` : 아래 표의 원본
- `abr.csv` : ABR 구간 1초 단위

용어

- 손실률: 재전송 받기 전 기준. 최종 손실률: NACK로 복구한 뒤에도 못 받은 비율
- 받은 영상: 30초 동안 받은 영상 분량(초). 서버가 3초 앞서 보내서 정상이면 33초쯤 나옴
- 멈춘 시간: 30초 중 버퍼가 비어서 재생이 멈춘 시간 (PC 클라이언트 추정치, 아래 주의 참고)

## 3. 결과에서 볼 것

**TCP는 손실이 안 보이는 대신 시간으로 치른다**
모든 조건에서 TCP 손실률은 0%. 대신 손실 5% + 지연 100ms에서 수신 속도가 585kbps로 떨어져서 30초 동안 영상을 6.1초 분량밖에 못 받았고 20초를 멈춰 있었다. 같은 조건에서 UDP는 2,706kbps를 유지하고 안 멈췄다. 대신 5.13%를 잃었다.

**TCP는 손실만 있을 땐 멀쩡하고, 지연이 같이 있어야 느려진다**
손실 5%만 걸었을 때 TCP는 2,832kbps로 정상과 같다. Mathis 공식 `1.22 * MSS / (RTT * sqrt(p))`으로 계산하면

| 조건 | RTT | 처리량 상한 | 720p(2.8Mbps) 가능? |
|---|---|---|---|
| 손실 1% | 10ms | 약 14.2 Mbps | 가능 |
| 손실 5% | 10ms | 약 6.4 Mbps | 가능 |
| 손실 5% + 지연 100ms | 110ms | 약 579 kbps | 불가 |

측정값 585kbps가 계산값 579kbps와 맞는다. RTT가 11배가 되니 상한이 1/11로 줄어든 것.

**NACK는 손실을 거의 다 복구하고, 비용은 손실률만큼**
손실 5%에서 최종 손실 0%, 재전송은 보낸 패킷의 4.7%. 손실 1%에서는 1.2%. 잃은 만큼만 다시 보내는 셈이라 TCP처럼 전체 속도를 줄이지 않는다.

**대역폭이 모자라면 TCP든 UDP든 NACK든 안 된다**
1Mbps에 2.8Mbps를 넣으면 TCP는 1/3 속도로 받느라 멈추고(받은 영상 10.7초), UDP는 65%를 잃는다. NACK를 켜도 재전송이 같은 병목을 지나야 해서 최종 손실 66%로 차이가 없고 오히려 손실률만 올라간다(64.7% -> 71.3%). 이건 화질을 낮춰야 해결됨 (아래 ABR).

## 주의할 점 (보고서에 같이 적을 것)

- TCP 모드의 손실은 실제 손실이 아니라 모델. 앱에서는 TCP 세그먼트를 버릴 수 없어서 손실의 결과(재전송 대기 + Mathis 공식 처리량 상한)만 적용했다. 그래서 표의 TCP 585kbps가 공식과 맞는 건 당연한 결과고, 실제 TCP 구현(CUBIC 등)이면 수치가 다를 수 있다. UDP 쪽은 패킷을 실제로 버린 결과
- "멈춘 시간"은 PC 클라이언트가 "받은 영상 분량 - 지나간 시간"으로 추정한 값. 데이터가 제때 왔는지만 보고 디코딩이 되는지는 안 본다. 그래서 대역폭 1Mbps + UDP에서 0초로 나왔는데, 실제 폰에서는 손실 65%면 화면이 완전히 멈췄다 (5번 표). 이 칸은 PC 값을 그대로 믿으면 안 됨
- 지연 50ms + 지터 50ms에서 UDP+NACK의 재전송 비율이 24.9%로 나온 건 문제. 손실이 0%인데 재전송이 2,183개 나갔다. 빈자리를 발견하고 20ms 뒤에 NACK를 보내는데, 지터가 50ms라 그냥 늦게 오는 패킷까지 재요청한 것(불필요한 재전송). 24.9%는 재전송 상한(25%)에 걸린 값이라 상한이 없었으면 더 나갔을 것. 수신 kbps가 3,590으로 높게 나온 것도 이 때문. NACK 대기 시간을 지터에 맞춰 늘리면 고쳐질 걸로 보이는데 아직 안 고침
- 조건당 30초 1회 측정이라 통계적으로 엄밀하진 않음. 손실률은 랜덤이라 돌릴 때마다 조금씩 다르게 나온다
- 루프백이라 실제 RTT가 1ms 미만. 실제 와이파이에서는 기본 RTT가 15~35ms였다
